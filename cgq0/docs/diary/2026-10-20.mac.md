### 学到

- 上游 zai-org/ZCode 是"快照式"历史（`feat: update vX.Y.Z`、`chore: sync ZCode source`），main 领先自己的 tag，有 force-push 重写历史的可能——将来 sync 自动化要留 merge 失败兜底。
- 仓库内置 SEA 构建流水线（`apps/zcode-cli/packages/cli`，`pnpm --filter @zcode/cli sea --target <t>`）支持 6 平台单文件产物，交叉构建官方设计，原生搜索工具用仓库内置预编译包；只有 darwin 目标必须跑在 macOS runner（codesign）。
- `build:zcode` 的 tar.gz 发行包 node-pty 预编译不含 Windows——做跨平台 CLI 发行要走 SEA 路线，不是 tarball。

## 10:36 写入 .github/workflows：release-cli + sync-upstream

按“先 workflow 后本地编译”的顺序落地（理由：CI runner 代劳构建，本地环境可完全不装；自编译产物与 CI 产物在服务端同身份，1.5x 实测不受影响）。

- release-cli：三 OS 四目标矩阵（linux-x64 / win-x64 / darwin-x64 / darwin-arm64），全用上游自带 SEA 脚本；发版策略 cli-v<版本号>，版本不变只留 artifacts 不重复发 Release；dispatch 可 force 覆盖。
- sync-upstream：每日 05:17（北京）merge upstream/main，冲突自动开 issue 不推送；合并成功显式 dispatch release-cli——GITHUB_TOKEN 的 push 不连锁触发其他 workflow（GitHub 防递归设计），这个坑提前避掉了。
- 细节：ELECTRON_SKIP_BINARY_DOWNLOAD=1 跳过桌面端大二进制；darwin 目标必须跑 macos runner（codesign）；paths-ignore 把 cgq0/** 和 *.md 的推送排除在构建之外。
- 状态：待 push 后手动 workflow_dispatch 验证全链路，再开 cron 信任自动化。

## 20:57 同步路径教训：上游合并只走服务端单一路径

今天上游 3c5b2276（v3.16.2 快照）进来时，本地手动 merge（ad1db1fc）和网页 Sync fork（5ad928cc）同时发生，产生两个树内容完全等价的孪生合并提交，远端还基于自己的那个发了版。处置：确认 `git diff HEAD origin/main` 为空后 `git reset --hard origin/main`，丢弃本地合并（无独有内容）。

**规矩**：上游同步以服务端为唯一入口（sync-upstream cron / 必要时网页 Sync），本地只 `git pull` 对齐，不再主动 merge upstream——除非正在本地做开发且确实需要提前拿到上游改动。
