# 2026-10-27 · win

## 23:30 — cq.75 win 包两问题实测：CLI TUI 在 SEA 下段错误（unsafe-pointer 静态导入 NODE.EXE）根因闭合 + CI 修复

**背景**：用户在 Windows 实测 cq.75 release zip 报两个问题：CLI 无法运行、Web 版
发消息报错。origin 无新 push（HEAD=f7e6cf5c，zip SHA256 与 SHA256SUMS-win-x64.txt
一致，产物即该 commit 构建）。Web 版问题（spawn EFTYPE，zcode-serve 的
GLM_BINARY_PATH 指向 zcode.cjs 被 resolver 当原生二进制直接 spawn；Linux 靠
shebang 命中系统 node 才幸存）由另一台机器修复中，本机只接 CLI。

**现象**：zcode-cli.exe 的 --version/--help/doctor/-p/app-server 全正常，唯独 TUI
（无参数或 tui 子命令）启动即崩，退出码 0xC0000005；真 TTY（独立控制台窗口）同崩。
开发版（node 直跑 zcode.cjs）TUI 正常存活 → 排除 TUI 代码本身。

**根因链**（逐步二分，每步都有对照实验）：

1. SEA 首次运行把 TUI runtime 解包到 `%LOCALAPPDATA%\zcode\Cache\sea-assets\`，
   5408 个文件逐一 sha256 对 manifest 全过 → 排除资产损坏。
2. 解包产物里 opentui.dll / koffi.node / unsafe-pointer.node 与本机
   node_modules 同名文件哈希完全一致 → 排除文件差异。
3. node 22.16 / 24.13 直跑 opentui-core（import 即走 FFI 后端加载）正常 →
   排除 Node 版本与 DLL 本身。
4. 最小 SEA 复现（D:\temp\sea-mini\：同一 node.exe 拷贝打底 + postject 注入
   「import opentui-core」脚本，隔离单变量）：node 直跑 OK，SEA 必崩（SIGSEGV）
   → 锁定 SEA 形态。
5. 二分到函数级：SEA 里 `require('koffi')`（加载 koffi.node）✅；
   `koffi.load(opentui.dll)` ✅；`require('unsafe-pointer.node')`（node-gyp-build
   走 process.dlopen）**当场段错误** ❌。
6. Node 24.22.1 重打 SEA 同崩 → 排除升级 Node 修复的可能；上游
   unsafe-pointer 0.2.0-next.de5d24e 预发布同崩 → 排除等上游新版。

**机制**（PE 导入表对比实锤，`unsafe-pointer.node | TLS目录:true | 导入DLL:NODE.EXE,...`
vs `koffi.node | 导入DLL:KERNEL32,ADVAPI32`——koffi 根本不静态导入 node.exe）：
zig 工具链（zig dlltool 生成导入库）把 napi_* 全部**静态按模块名导入 NODE.EXE**。
普通 node 进程主模块就叫 node.exe，加载器按名命中已加载实例，单实例无恙；SEA
进程主模块名是 zcode-cli.exe，加载器按 DLL 搜索路径找到**磁盘上的真 node.exe**
（PATH 里就有）把它当依赖**二次加载**，addon 的 IAT 指向第二个 node 实例，而
napi_env 指向 SEA 进程自己的实例——跨实例访问 → 段错误。koffi/pty 是
node-gyp/MSVC 系（delay-load：首次调用经 GetModuleHandle 解析进程主模块，与主
模块叫什么名字无关），所以 SEA 兼容。一个反直觉的中间观察：SEA 里
`koffi.load(unsafe-pointer.node)` 能"成功"——LoadLibrary 完整走完（双实例已
形成），只是没调 napi_register 所以没崩，属"成功但有毒"。

**修复**（本机无 MSVC、无 Windows SDK、rustc 无 linker、zig/npmjs 下载不通，
本地编译路线全灭 → 借 CI runner 的 MSVC）：release.yml win leg 在 pnpm install
后用 `npx -y node-gyp@11 rebuild` 就地重编译 unsafe-pointer（包内自带 binding.gyp
+ src/binding.c，标准 N-API C，无特殊依赖）并覆盖 prebuilds/win32-x64/
unsafe-pointer.node——node-gyp 产物天然 delay-load，后续 sea-tui-assets 收集与
运行时 node-gyp-build 查找都命中 prebuilds 路径，SEA 资产里带的即 MSVC 版。
darwin/linux 的 zig prebuild 走平台动态符号解析（mac 是 undefined dynamic_lookup
语义），无此问题，不动。

**CI 为什么一直绿**：build-sea 的 smokeTestHostTarget 只跑 `--version`，TUI 原生
闭包只在 zcode-tui-runtime 资产解包后才加载。补「Smoke test SEA TUI」步骤：四个
leg 都是 host 构建，SEA 产物跑 `tui < /dev/null` 断言 exit 1 且输出含
"interactive terminal"（修复前 win 实测 bash 下 exit 139）；macOS 无 GNU timeout
用 gtimeout 探测。

**遗留**：修复假设的最终裁判是 dispatch 重跑 release workflow 的 tui 冒烟（本机
无 MSVC 无法本地预编 node-gyp 产物）。根治上游化（unsafe-pointer 换 MSVC/
delay-load 工具链出 prebuild）值得给 justjake/node-unsafe-pointer 报 issue，材料
即本条根因链，待定。另：Web 版首用需先建项目并把输入框上下文从「不在项目中工作」
切过去，否则 project.remote-project-required 在 UI 只显示"草稿会话创建失败"，
排查不友好（上游 UX 问题，记录备查）。

## 00:59 — CI 修复落地：六轮迭代后 cq.82 全绿，四平台 SEA tui 冒烟通过

**修复形态**（上条的方案落地）：release.yml win leg pnpm install 后
`npx -y node-gyp@13 rebuild` 就地重编 unsafe-pointer 覆盖 win32-x64 prebuild
（node-gyp/MSVC 走 delay-load，不按模块名绑 NODE.EXE）；四个 leg SEA 产物跑
`tui`（非 TTY）断言 exit 1 + "interactive terminal"——崩溃退出码（139/
3221225477 等）即护栏报警。CI 是 MSVC 编译的唯一可用场（本机无 MSVC/SDK，
rustc 无 linker，zig/npmjs 下载不通）。

**六轮踩坑**（每轮根因均实证，全在 release.yml 单文件内修）：

1. run 40532699443：`require.resolve('unsafe-pointer/package.json')` 报
   ERR_PACKAGE_PATH_NOT_EXPORTED（该包 exports 未暴露子路径）→ 改 resolve
   包入口取 dirname；同时 node-gyp@11 的 find-visualstudio 不识别 runner 新
   VS 18/2026（报 unknown version "undefined"，同 run 里 pnpm install 的
   cpu-features@node-gyp@11.5.0 同样构建失败仅因 optional 未阻塞）→ 升
   node-gyp@13（12.1.0 加 VS 2026 支持、13.0.1 修版本解析，CHANGELOG 实证）。
2. run 40535391823：node-gyp@13 编译成功（gyp info ok），但 binding.gyp 的
   target_name 是 node_unsafe_pointer，产物名与发布名不同，cp 按
   unsafe-pointer.node 找不到 → 两边各用其名。
3. run 40536478016：冒烟 exit 127——按 `zcode-${target}.exe` 拼出
   zcode-win-x64.exe，产物实为 zcode-windows-x64.exe（win→windows 映射差，
   linux/darwin 恰同名不炸）→ case 全映射对齐 Package 步骤。
4. run 40537736131：**win/linux 双绿——rebuild 与 SEA tui 冒烟双双通过，
   修复在 CI 验证成立**；mac 两 leg 排队 15 分钟未分配 runner 被 cancelled
   （runner_name 空；GitHub 官方 capacity 告示），release skipped。
5. run 40540577375：mac 排上了，但 darwin 冒烟零输出即死——
   `to=$(command -v timeout || command -v gtimeout)`：macOS 两者皆无，||
   链尾非零退出码成为赋值退出码，bash -e 静默杀脚本（连第一行 echo 都没跑，
   SEA 实际没执行，darwin TUI 健康度仍未测到）→ 冒烟改 node 内联包装
   （三平台必有 node）：spawn + 90s 超时 + SMOKE_EXIT:<code> 输出，本机验证
   三场景（--version EXIT:0 / cq.75 旧 SEA tui EXIT:3221225477 / 逻辑自检）。
6. run 40542414615：**全绿**（win/linux/darwin-arm64/darwin-x64 四 leg +
   release job），Release 资产刷新为 cq.82.g829a1523。darwin 冒烟通过顺带
   证实 mac zig prebuild 走平台动态符号解析，无 win 的静态绑定问题——
   修复仅需 win leg 成立。

**教训**：CI 步骤脚本要按"每轮只引入一个变量"写——本轮四个坑（exports/
target_name/产物名映射/timeout 探测）全是可以在第一轮就防掉的：解析包根与
产物名应以实际文件为准（ls 验证）而非想当然；跨平台 shell 片段里
`var=$(cmd || cmd2)` 在 set -e 下的退出码传播是经典暗雷，凡"探测型赋值"必须
`|| true` 兜底或改用显式 if。macos-latest 排队 cancelled 是时段性容量问题，
错峰重触发即可，不是仓库侧问题。

**端到端余项**：cq.82 win zip 真机 TUI 复验（下载中；CI 冒烟已是最强证据——
SEA tui 在 win runner 真实执行并优雅退出，而非崩溃）。
