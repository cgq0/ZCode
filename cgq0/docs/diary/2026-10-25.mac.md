背景两件：用户本地试用构建报 `cq.2`（v3.16.2 发版 tag 落在 fork 提交上，把 git describe
基线从「距官方同步点」重置成「距上次发版」；发布值 cq.41 恰为同步点基线纯属 CI 构建时

报告转写区 `+Thinking...` 静止分不清进行中/卡住，要求把 10-24 侧栏点动效扩到对话框。

**裁决（AskUserQuestion）**：基线锚点 = 最近官方同步合并提交（subject 含 `zai-org:main`
或 `upstream/main` 的 merge），不取 merge-base(upstream/main)——前者与已发布 41 连续
（dev=43），后者 CI 要额外 fetch upstream 且数字断档（发布时会是 47）。

实现要点：
- 基线算法单点收进 `scripts/fork-build-meta.mjs`（同步 API：desktop build-meta 落盘是
  同步链路，async 化会波及 about 消费方；execFileSync + execGit 注入可测）。cli
  build.mjs / desktop build-metadata.mjs / release.yml 两段 inline 此前逐字复制三份
  describe 解析，本次一并消除；release.yml 输出加严格形态校验
  （`cq.[0-9]*.g[0-9a-f]*`，落到 cq.dev 形态直接 fail——CI 有全量历史，降级即假设已破）。

  不算 dirty）。
- spec `2026-10-21-fork-build-metadata` 顺带回写 10-24 三产物发版的 tag/zip 事实
  （tag `v<根版本>`、zip `zcode-v*-<meta>-<target>`——此前漏更，spec 还停在 zcode-cli-v*）。
- 动效：帧所有者仍唯一（AppView `useThinkingDots` 400ms，零新增 timer），门控
