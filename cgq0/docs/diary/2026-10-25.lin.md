## 09:47 — fork 视觉身份批次：ZCode.fork 产品名 + 蓝底图标（与官方版可同装）

**背景**（mac 上与官方版的共存问题，三轮讨论收敛）：

1. fork CI（release.yml）桌面产物是 `ZCODE_ENV=production` 的 production 身份，
   appId/userData 与官方 `ZCode.app` 全同：拖进 /Applications 直接顶掉官方，
   换目录装也躲不开（冲突跟 bundle id / userData 走，与安装路径无关）。
2. 仓库自带 Preview 身份（`dev.zcode.app.preview`）能真并存，但它把 Electron
   userData 拆开（登录态/窗口状态分家）——与"数据共享本来就是期望功能"相反，弃用。
3. 收敛到需求本质：**要的是"可同装 + 可区分 + 数据共享"，不需要同时运行**。

**决策**：保持 production 身份（appId `dev.zcode.app`、userData `~/Library/
Application Support/ZCode` 都不动 → 登录态/任务/凭据与官方全共享，单实例锁天然
防止双开），只改两个显示层：产品名 `ZCode.fork` + 图标黑底换蓝底。Finder 里
`ZCode.fork.app`（蓝）与 `ZCode.app`（黑）名字图标双区分，互不覆盖。

**实现**：

- `desktop-product-identity.mjs` 新增 `ZCODE_DESKTOP_PRODUCT_NAME` 覆盖：只改
  productName（.app 名/菜单栏/About/${productName} 产物名），flavor/appId/
  AUMID/Linux 包名/userData 目录名全部保持 flavor 原值。未设或空白 = 原样返回
  冻结身份表对象（存量测试的 `toBe` 语义不破坏）；含路径分隔符构建期报错。
  名字故意取通用拼写而不是 ZCODE_FORK_*，让这个 diff 对上游像个正经功能。
- `cgq0/scripts/rebrand-icons.py`（fork 命名空间，lin 机跑，需 Pillow）：
  近黑低饱和背景（max≤0x40 且极差≤14）映射为纵向蓝渐变（#1D4ED8→#1E3A8A），
  按原亮度/BG_REF=0x19 缩放保留原图渐变、暗角与底部纯黑投影层次；白 Z
  （min≥0xC0）原样；中间调按亮度比例蓝白混合保抗锯齿；alpha 全程不动。
  icns/ico 从换色源图重生成；上游换图标后重跑即可。`--apply` 覆盖
  packages/desktop/build/ 下 16 个资产（icon/icon_windows/icon_installer ×
  png/icns/ico + icons/ 尺寸集；icon_windows 与 icons/1024 本是同一文件）。
- release.yml desktop 步骤注入 `ZCODE_DESKTOP_PRODUCT_NAME: "ZCode.fork"`，
  release notes 表格/安装说明/Gatekeeper 提示文案同步（改为"可同装互不覆盖，
  数据共享、同时只运行一个"）。

**验证**：

## 10:45 — fork Actions 被 GitHub 静默禁用：定位、恢复、两项裁决

**事件**：上面批次的 4 个 commit 推 main（b923ad84，09:57）后 release 零触发；
补空 commit 再推（1c3540cf）依旧零触发。push 本身都成功（commits API 确认
ref 更新）。

**定位链**（下次照抄，别再从头排查）：

1. push 落库但 run/suite 为 0，`check-suites` 新旧 commit 对照（老 2 / 新 0）
   是最快的判定；
2. workflow `state: active`、permissions 正常、YAML 合法、触发条件匹配、
   githubstatus 全绿——**这些 API 在此场景下全部说谎**；
3. 双路确认非缓存（本机 curl + 服务端 WebFetch 同结果）；
4. `ssh -T git@github.com` 排除 deploy key（deploy key 推送不触发事件是
   官方规则；本机是 cgq0 个人 key，"Hi cgq0!"）；
5. 根因：community #210951——**2026-10-14 起 GitHub 对公开 fork 静默禁用
   Actions**，文档称 "GitHub-controlled disabled state"，改设置/API 均无效，
   唯一真话是网页 Actions 页的横幅（带"上游已构建、fork 重复跑是浪费"说明
   与 enable 按钮）。无 changelog、无通知、support 工单自动关转自助。

**恢复**：Actions 页横幅手动 enable → release 用 workflow_dispatch 手动跑
（run #3，构建 1c3540cf，成功，Release 资产已刷新为 ZCode.fork 出包）。

**账号影响调研结论**（用户问"会不会影响账号"）：公开仓库标准 runner 免费
（billing 文档原文），$0 无账单；enable 是官方按钮无账号后果；真风险是
复发且无通知——sync-upstream 这类定时任务会一起静默停摆。

**裁决**：

1. **sync-upstream 摘掉每日调度**（保留 workflow_dispatch 手动触发）：
   Windows 默认官方版、mac 官方+fork 并存，上游有更新手动处理即可；也消掉
   最无感的停摆面。
2. **fork Actions 静默禁用应对进 TODOs**：症状=push 落库但零 run、API 全绿
   → 直接去 Actions 页看横幅手动 enable。

**事故自记**：我在同一消息里重复发了两条 reset --hard，多删一个已推送的
空 commit（1c3540cf），`git reset --hard origin/dev` 恢复无损失。教训：
重复的工具调用会各自真实执行，reset 类命令先想清楚执行次数再发。

**遗留**：push 触发是否随 enable 恢复未验证（1f3540cf/1f39265a 的推送都
早于或混在 enable 时间点里）；本批 main 推送即验证——若 run #4 未自动
出现，说明 push 事件仍被吞，后续 main 推送都要记得手动 dispatch release。
